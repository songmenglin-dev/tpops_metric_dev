# GaussDB 指标与告警采集端 —— 部署运行说明

本文面向**客户侧运维人员**。照着本文走完，客户环境上就能跑起一个常驻采集端：
从 TPOPS（GaussDB 监控平台）按周期拉取指标与告警，按 ITSCADA 字段规范转成 JSON，
投递到 Kafka（PLAINTEXT），由客户监控平台消费。

采集端是**常驻进程**，不是一次性脚本：拉取 → 转换 → 投递 → **投递成功后才推进水位**，
投递失败不推进水位，重启后从水位续传（**至少一次**语义）。

---

## 1. 前置条件

| 项 | 要求 | 说明 |
|---|---|---|
| 操作系统 | Linux（x86_64） | 已在 CentOS / Ubuntu 上验证；其他发行版需自行确认 `openssl` 与 `librz` 等基础库 |
| Python | **3.7.9** | 硬性要求。代码有 3.7 语法红线（不用海象、字典合并、内建泛型注解等），3.8+ 可运行但**未验证**，3.7.9 是唯一验收过的版本 |
| 依赖 | `requests>=2.25,<2.32`、`kafka-python==2.0.2` | 见 `requirements.txt`。**不要擅自升级**：`kafka-python` 2.1+ 已不支持 3.7；`requests` 2.32 起要求 Python ≥ 3.8 |
| Kafka | 客户端可连的 broker，**PLAINTEXT** 协议 | 需预先创建两个 Topic（指标 / 告警），并与采集端的配置一致；分区数也要一致（见 §3 `KAFKA_TOPIC_PARTITIONS`） |
| TPOPS 平台 | 可访问的平台地址 + **有权限的账号** | 账号需要能访问：实例列表、监控指标、告警记录、命令中心、诊断优化五个接口集 |
| 平台证书 | 平台使用**自签证书** | 客户端默认**不校验**证书（`TPOPS_VERIFY_TLS=false`）。若客户要求校验，需自行导入平台证书并把该变量置 `true` |
| 磁盘 | 状态目录可写 | 水位文件每轮落盘一次，目录不可写会导致重启后水位丢失（数据整段重投） |
| 出站网络 | 采集端 → TPOPS（https）、采集端 → Kafka（PLAINTEXT） | 两个方向都要通 |

> **平台接口路径有两套命名空间，不能混**：`/rds/v3/…`（认证、实例列表、监控指标、告警）
> 与 `/rds/gaussdb/v3/…`（诊断优化 + 统一命令中心）。少一段前缀就是 404。
> 采集端已按正确路径实现，**运维侧不需要**在代理/网关上做额外改写。

## 2. 部署步骤

采集端是**独立可部署产物**：只需要 `tpops_kafka_collector/` 一个目录，
不需要整个仓库、不需要 `data/`、不需要 `tools/`。

```bash
# 1) 拷贝产物（连同 requirements.txt）
mkdir -p /opt/tpops-collector
cp -r tpops_kafka_collector /opt/tpops-collector/
cp requirements.txt /opt/tpops-collector/

# 2) 准备 Python 3.7.9 环境
conda create -n tpops python=3.7.9 -c conda-forge --override-channels -y
conda install -n tpops -c conda-forge --override-channels -y pip
conda run -n tpops python -m pip install -r /opt/tpops-collector/requirements.txt

# 3) 准备环境变量
cp /opt/tpops-collector/.env.example /opt/tpops-collector/.env
vi /opt/tpops-collector/.env      # 至少填 TPOPS_PASSWORD 与 KAFKA_BOOTSTRAP_SERVERS
chmod 600 /opt/tpops-collector/.env   # 文件里有口令

# 4) 启动
cd /opt/tpops-collector
set -a && source .env && set +a
conda run -n tpops python -m tpops_kafka_collector.main
```

> `.env.example` 是**完整 30 项**配置清单（每项都有中文注释：用途、默认值、改错的后果）。
> 只填必填项也能跑 —— 必填项只有 `TPOPS_USER`、`TPOPS_PASSWORD`、
> `KAFKA_BOOTSTRAP_SERVERS` 三项，其余取默认值。

### systemd 单元（参考）

```ini
[Unit]
Description=GaussDB TPOPS Kafka Collector
After=network-online.target

[Service]
Type=simple
User=tpops
WorkingDirectory=/opt/tpops-collector
EnvironmentFile=/opt/tpops-collector/.env
ExecStart=/opt/conda/envs/tpops/bin/python -m tpops_kafka_collector.main
Restart=always
RestartSec=10
# 停机要给足时间：收尾（等在途请求 + 落水位 + flush Kafka）最长 30 秒
KillSignal=SIGTERM
TimeoutStopSec=45

[Install]
WantedBy=multi-user.target
```

> `systemctl stop` 发的是 **SIGTERM**，采集端会走**优雅退出**（见 §4）；
> `kill -9`（SIGKILL）**不会**执行收尾 —— 水位可能丢一轮，重启后那一轮会被重投
> （客户侧按幂等键去重，不会产生重复数据）。

## 3. 环境变量

全部配置**只从环境变量读取**，启动时一次性加载成不可变对象，运行期间不再读环境变量。
必填项缺失或取值非法 → **启动即失败**（不发任何请求），退出码 **2**。

### 3.1 TPOPS 平台

| 变量名 | 默认值 | 必填 | 说明 | 改错的后果 |
|---|---|---|---|---|
| `TPOPS_USER` | —（示例文件里是 `sml`） | **是** | 平台登录用户名（mini-token 认证用） | 缺失 → 退出码 2；用户名错 → 认证失败，进入静默期并可能锁号 |
| `TPOPS_PASSWORD` | — | **是** | 平台登录密码 | 缺失 → 退出码 2。**口令只走环境变量，不写日志、不进异常消息、不进健康检查响应** |
| `TPOPS_BASE_URL` | `https://172.16.103.193:8002` | 否 | 平台地址（含端口） | 连不上平台 → 所有通道全部失败 |
| `TPOPS_VERIFY_TLS` | `false` | 否 | 是否校验平台证书（`true/false/1/0/yes/no/on/off`） | 平台是自签证书；置 `true` → TLS 握手失败，全部请求报错 |
| `TPOPS_REQUEST_TIMEOUT` | `60` | 否 | 单个 TPOPS HTTP 请求超时（秒），取值 ≥ 1 | 过小 → 慢响应被当成超时、命令中心频繁重试；过大 → 平台卡死时进程长时间挂住 |
| `TPOPS_AUTH_FAILURE_COOLDOWN_SECONDS` | `60` | 否 | 认证失败后的静默期（秒），取值 ≥ 0；`0` = 关闭 | 平台的认证失败会累计 `login_failed_attempts` 并**锁号**。静默期过小 → 仍会撞上锁号；过大 → 改完密码后要等很久才恢复 |

### 3.2 Kafka

| 变量名 | 默认值 | 必填 | 说明 | 改错的后果 |
|---|---|---|---|---|
| `KAFKA_BOOTSTRAP_SERVERS` | — | **是** | broker 地址，逗号分隔；PLAINTEXT | 缺失 → 退出码 2；地址错 → 投递全部失败（投递失败不推进水位，重投直到成功） |
| `KAFKA_TOPIC_METRICS` | `gaussdb.metrics` | 否 | 指标消息的 Topic 名 | 与客户订阅的 Topic 不一致 → 客户侧看不到指标 |
| `KAFKA_TOPIC_ALARMS` | `gaussdb.alarms` | 否 | 告警消息的 Topic 名 | 同上 → 客户侧收不到告警 |
| `KAFKA_TOPIC_PARTITIONS` | `4` | 否 | Topic 分区数，取值 ≥ 1 | 与客户预建的 Topic 分区数不一致 → 生产者报「Topic 已存在但分区数不符」 |
| `KAFKA_COMPRESSION` | `lz4` | 否 | 压缩算法；`none/gzip/snappy/lz4/zstd` | 取值不在允许集合 → 退出码 2 |

### 3.3 调度与指标窗口

| 变量名 | 默认值 | 必填 | 说明 | 改错的后果 |
|---|---|---|---|---|
| `POLL_INTERVAL_SECONDS` | `30` | 否 | 调度轮询间隔（秒），取值 ≥ 1 | 调大 → 各通道实际刷新周期被拉长（周期 = 轮询间隔）；调得过小（< 10）→ 平台压力大 |
| `METRIC_WINDOW_HOURS` | `2` | 否 | 指标查询窗口（小时），取值 ≥ 1 | **不得小于 1** —— 小于 1 小时覆盖不到 3600s 采集周期的指标，该指标大面积 null |
| `METRIC_END_LAG_MINUTES` | `5` | 否 | `end_time` 回退量（分钟），取值 ≥ 0 | 平台数据入库滞后约 5 分钟，不回退 → 尾部大量 null；回退过大 → 数据偏旧 |

### 3.4 命令中心（统一命令中心 SQL 通道）

| 变量名 | 默认值 | 必填 | 说明 | 改错的后果 |
|---|---|---|---|---|
| `CMD_CONCURRENCY` | `2` | 否 | 并发下发的命令条数，取值 1~10 | 调大 → 平台加压、轮询超时率升高，可能触发限流整轮失败；超过 10 → 退出码 2 |
| `CMD_LIMIT` | `1000` | 否 | 单条命令的 `limit` 行数，取值 1~1000（平台硬上限） | 改小于实际行数 → **静默截断**（部分指标少数据且不报错）。注：当前实现未消费本项 |
| `CMD_PAGE_SIZE` | `100` | 否 | 合并 SQL 分页容量（每页每个视图取多少行），取值 1~1000 | 平台单次输出上限 102400 B，超了**整条任务失败**（不是截断）；调大易触顶，调小则翻页变多 |
| `CMD_POLL_TIMEOUT` | `60` | 否 | 命令中心任务轮询超时（秒），取值 ≥ 1 | 单次往返实测 3~8 秒；过小 → 误判超时并触发重试 |
| `CMD_RETRY_ATTEMPTS` | `3` | 否 | 单条命令的失败重试次数，取值 ≥ 0 | 实测 50 条 SQL 有 3 条偶发失败（重试即成功）；置 `0` → 偶发失败直接丢数据 |

### 3.5 告警

| 变量名 | 默认值 | 必填 | 说明 | 改错的后果 |
|---|---|---|---|---|
| `ALARM_LIMIT` | `100` | 否 | 告警接口单页条数，取值 1~100（平台硬上限） | 超过 100 → 退出码 2；不翻页 → 靠水位续传补 |
| `ALARM_RETENTION_DAYS` | `30` | 否 | 平台历史告警保留窗口（天），取值 ≥ 1 | 平台只保留 30 天历史告警。本项用于判断「拉到的历史告警是否已超出平台保留期」并显式告警 |

### 3.6 慢 SQL 脱敏

| 变量名 | 默认值 | 必填 | 说明 | 改错的后果 |
|---|---|---|---|---|
| `SQL_MASKING_ENABLED` | `true` | 否 | 是否对慢 SQL 文本脱敏 | 关闭后 SQL 原文会外发到客户监控平台 —— **需客户书面确认**才能关 |
| `SQL_TEXT_MAX_LENGTH` | `512` | 否 | 慢 SQL 文本最大长度（字符），取值 ≥ 1；超出截断并显式标记 | 过大 → 消息体膨胀；过小 → SQL 失去排障价值 |

### 3.7 通用重试

| 变量名 | 默认值 | 必填 | 说明 | 改错的后果 |
|---|---|---|---|---|
| `RETRY_MAX_ATTEMPTS` | `5` | 否 | 通用重试最大尝试次数，取值 ≥ 0 | 注：当前各调用点的重试次数由各自配置固定（命令中心用 `CMD_RETRY_ATTEMPTS`），本项**尚未被消费**，改动不影响当前运行行为 |
| `RETRY_BASE_SECONDS` | `1.0` | 否 | 退避基数（秒），取值 ≥ 0；指数退避 1→2→4→8 | 命令中心 SQL 重试的退避基数取自这里；过大会拖慢失败恢复，过小则可能连续打在故障的平台上 |

### 3.8 运行时（状态目录 / 健康端点 / 日志）

| 变量名 | 默认值 | 必填 | 说明 | 改错的后果 |
|---|---|---|---|---|
| `STATE_DIR` | `./state` | 否 | 状态目录（相对当前工作目录） | 目录不可写 → 每轮落盘失败，重启后水位与去重状态全丢（数据整段重投） |
| `HEALTH_HOST` | `127.0.0.1` | 否 | 健康端点监听地址 | 改成 `0.0.0.0` 会把健康端点暴露到网络上 |
| `HEALTH_PORT` | `8088` | 否 | 健康端点监听端口，取值 1~65535 | 端口被占用 → 装配失败，退出码 **3** |
| `LOG_LEVEL` | `INFO` | 否 | `DEBUG/INFO/WARNING/ERROR/CRITICAL` | 取值不在允许集合 → 退出码 2；置 `DEBUG` → 日志量明显增大 |
| `LOG_FORMAT` | `text` | 否 | `text`（人读：`时间 \| 级别 \| 模块 \| 消息`）或 `json`（给日志平台按字段取） | 取值不在允许集合 → 退出码 2 |

## 4. 启动与优雅退出

### 4.1 启动

```bash
python -m tpops_kafka_collector.main
```

进程职责：**装 → 起 → 收信号 → 优雅退 → 退出**。

- 启动期依次完成：加载并校验配置 → 从状态目录恢复水位 / 差分基线 / 幂等键 →
  平台画像（发现一次 → 固化 → 之后以文件为准）→ 装配 Kafka 生产者、五个采集器、
  调度器、健康端点。
- **TPOPS 认证是惰性的**：首次真正发请求时才认证。
- 平台画像不存在时自动发现一次并固化到 `platform_profile.json`；
  之后**不再重新发现**（每轮重新发现会导致「静默增删采集目标」，水位与差分基线全部错位）。

**退出码**：

| 退出码 | 含义 |
|---|---|
| `0` | 正常退出（收到 SIGTERM / SIGINT 后优雅退出） |
| `2` | 配置缺失或非法（必填项没填、数值越界、枚举取值非法） |
| `3` | 装配失败（依赖装不起来，例如健康端点端口被占用） |

### 4.2 优雅退出

收到 **SIGTERM**（`systemctl stop`）或 **SIGINT**（Ctrl-C）后：

```
置位 shutdown（执行器不再发起新的 HTTP 请求）
  → 停发新任务；在途请求最多等 30 秒（超时即放弃，不挂死）
  → 原子写水位
  → flush / 关闭 Kafka producer
  → 退出码 0
```

要点：

- **停机后不再发起新的 HTTP 请求** —— 检查落在执行器层，已经排进线程池但没开始跑的任务
  也不会再发请求。
- **最多等 30 秒**：在途请求超时就**放弃等待**，进程照常退出，不会被一个挂死的
  HTTP 调用拖住。
- 退出走 `os._exit()`，**跳过 atexit 钩子**（Python 3.7 的线程池退出钩子会
  `join()` 所有工作线程，一个挂死的请求就能把进程拖住）。收尾（水位落盘 + producer flush）
  在此之前已经做完。
- **正常退出不会丢水位**：水位每轮结束就落盘一次（不是只在退出时落盘），
  崩溃最多丢一轮。

## 5. 运行期文件

全部在 `STATE_DIR`（默认 `./state`）下：

| 文件 | 内容 | 运维须知 |
|---|---|---|
| `watermark.json` | 水位文件：指标水位、告警水位、差分基线、已投递的幂等键集合 | **自动维护，不要手改**。每轮落盘一次（原子写：写临时文件 + `os.replace`）。删除它 = 清空去重状态 = 下一轮把这段数据整段重投 |
| `platform_profile.json` | 平台画像：采集哪些实例、实例名、`mode`、引擎名/版本、master 节点数 | **可以手工编辑** —— 换实例 / 加实例 / 删实例都改这个文件，改完下一轮启动生效，不需要改代码、不需要改配置。平台新增实例**不会**自动加入采集（自动加 = 每轮重新发现 = 水位错位），日志会明确提示「平台新增了实例 …… 需人工更新（删除画像文件可重新发现）」 |

**换实例的两种做法**：

1. 改 `platform_profile.json`（推荐）：编辑 `instances` 数组，保留 `version: 1` 字段。
2. 删除 `platform_profile.json` 重启：采集端会重新发现并**采集平台上的全部实例**。

**画像核对**：每次启动会顺手拿画像与平台现状对一遍，**只记日志、不改文件**：

| 不一致项 | 日志级别 | 处置 |
|---|---|---|
| 画像里的实例在平台上已不存在 | ERROR | 人工确认（被删还是被重建） |
| 平台上有画像没记录的实例 | WARNING | 确认后手工加进画像文件 |
| 引擎名变了（平台升级） | WARNING | 指标码可能已变，映射表可能需要重新生成 |
| master 节点数变了（扩缩容） | WARNING | 多 master 归集口径要复核 |

## 6. 健康检查

两个端点，**语义必须分开**（混为一谈会有真实代价：编排器若把 liveness 挂在依赖上，
一次 Kafka 抖动就会把采集端反复重启，重启又让水位重放，问题被放大）。

| 端点 | 语义 | 响应 |
|---|---|---|
| `GET /healthz` | **存活** —— 进程能应答就是 200。**不看任何依赖** | `200` + `{"status":"ok","check":"liveness","timestamp":…}` |
| `GET /readyz` | **就绪** —— 依赖不可用时返回 **503**，告诉编排器「先别派活给我」 | `200` / `503` + `{"status":…,"check":"readiness","dependencies":[{"name":…,"ready":…,"reason":…}]}` |

### `/readyz` 返回 503 的两种情况

1. **TPOPS 未认证**（探针 `tpops`）：尚未完成认证、或最近一次认证失败 →
   `reason` 为「TPOPS 尚未完成认证」/「TPOPS 最近一次认证失败」。
2. **调度器最近一次成功采集超过 180 秒**（探针 `scheduler`）：还没成功完成过一轮
   → 「调度器还没有成功完成过一轮采集」；或距最近一次成功采集已超过 180 秒
   → 「最近一次成功采集距今超过 180 秒」。

探针**只读已维护的状态标志位**，不在探针里 ping 平台、不连 Kafka（探针本身不能变成故障源）。
单个探针抛异常不会拖垮端点 —— 该依赖记为不就绪。**响应体不含任何凭据**
（口令与 Kafka 连接串里的用户信息都有兜底脱敏）。

用法：

```bash
curl -s http://127.0.0.1:8088/healthz
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8088/readyz   # 期望 200
```

> 默认只监听回环（`127.0.0.1:8088`）。要给编排器探针用，需要改 `HEALTH_HOST`
> —— 改了就是把它暴露到网络上，请评估网络策略。

## 7. 日志

- 输出到 **stderr**（常驻进程的标准做法；日志轮转是运维的事，采集端不自己写文件）。
- `LOG_LEVEL` 默认 `INFO`；`LOG_FORMAT` 默认 `text`：
  - `text`：`2026-11-24 10:00:00,123 | INFO | tpops_kafka_collector.scheduler | ...`
  - `json`：每行一个 JSON 对象。轮询汇总行（`tick=… elapsed=… fetched=…`）会被
    **摊平成顶层字段**，客户侧日志平台可以直接按字段取，不用去解析 message 字符串。
- **第三方库已降噪**：`kafka` / `kafka.conn` / `kafka.cluster` / `urllib3` / `requests`
  压到 `WARNING`，不刷屏。
- **敏感信息不入日志**：口令、mini-token、业务 SQL 文本都不进日志；
  日志配置是幂等的（重复调用不会叠加 handler）。

## 8. 排障

| 症状 | 可能原因 | 处理 |
|---|---|---|
| 启动即退出，日志「缺少必填环境变量：XXX」，退出码 2 | 必填项没配 | 补 `TPOPS_USER` / `TPOPS_PASSWORD` / `KAFKA_BOOTSTRAP_SERVERS`；检查 `set -a && source .env && set +a` 是否执行过 |
| 启动即退出，日志「配置校验失败 …… 超出允许范围 / 不在允许取值内」，退出码 2 | 数值越界或枚举值写错 | 按 §3 表格的取值范围改（如 `CMD_CONCURRENCY` 只能 1~10，`ALARM_LIMIT` 只能 1~100） |
| 退出码 3，日志「装配失败」 | 端口被占用（`HEALTH_PORT`）、Kafka 客户端构造失败 | 换 `HEALTH_PORT`；检查 broker 地址是否可达 |
| **平台认证失败，日志报「认证失败」** | 用户名/口令错；或**累计锁号** | **平台的认证失败会累计 `login_failed_attempts` 并锁号** → **不要盲目重试**。采集端已内置 60 秒静默期（`TPOPS_AUTH_FAILURE_COOLDOWN_SECONDS`），期内不再发起认证。处理：确认口令正确 → 找平台管理员解锁 → 必要时把静默期调长。**手工反复 `curl` 试登录会加速锁号** |
| 某类指标大面积 `null` / 没消息 | 查询窗口太短，或 `end_time` 没回退 | `METRIC_WINDOW_HOURS` **不得小于 1**（否则覆盖不到 3600s 采集周期的指标）；`METRIC_END_LAG_MINUTES` 保持 ≥ 5（平台入库滞后约 5 分钟，不回退 → 尾部大量 null） |
| 日志「监控指标空分组告警：分组码 XXX 未返回任何指标」 | 分组码写错 | 平台对写错的分组码返回 **HTTP 200 + 空 series 且不报错**，只能靠这条日志发现。核对 12 个分组码 |
| 日志「监控指标分组目录全空：12 个分组码都没返回指标 —— 本轮 A 类无数据」 | 分组码全错，或认证后接口权限不足 | 先确认认证成功，再核对分组码 |
| 日志「告警历史缺口告警：最新历史告警时间距今 N 天，超过平台 30 天保留窗口」 | 停机时间超过平台保留期 | **平台历史告警仅保留 30 天**，这段时间的告警平台侧已清理，采集端**补不回来**。处理：缩短停机时间；长期停机场景需客户另建归档。日志会显式告警，不会静默 |
| 日志「命令中心 …… 重试后成功」 | 命令中心**单次往返 3~8 秒**，实测 50 条 SQL 有 **3 条偶发失败（重试即成功）** | **偶发失败会自动重试**（`CMD_RETRY_ATTEMPTS`，默认 3 次，指数退避）。偶发一次不用管；持续失败看是不是平台侧限流 → 调小 `CMD_CONCURRENCY` |
| 日志「命令中心返回了与上一页相同的内容……平台可能未生效 offset，本轮停止翻页」 | 平台未按 offset 分页 | 本轮停止翻页（防无限翻页卡死）。数据量大的实例考虑调小 `CMD_PAGE_SIZE` |
| 消息条数远多于预期（表级/库级指标） | **维度展开**：一行结果 = 一条消息 | 6000 张表 → 6000 条消息。这是设计口径（占位符指标按行展开），不是缺陷；确认 Kafka 侧吞吐与磁盘 |
| 投递失败，日志有 Kafka 异常 | broker 不可达 / Topic 不存在 / 分区数不符 | 投递失败**不推进水位** → 数据会重投，不会丢。修好 Kafka 后自动恢复。分区数不符时把 `KAFKA_TOPIC_PARTITIONS` 改成与客户预建 Topic 一致 |
| 重启后数据重复 | `STATE_DIR` 不可写，或水位文件被删 | 水位每轮落盘；确认目录可写、文件没被清。客户侧按幂等键去重，重复投递不会产生重复数据 |
| `/readyz` 一直 503，reason 是「TPOPS 尚未完成认证」 | 平台不可达或认证失败 | 见「平台认证失败」一行；先看认证相关日志 |
| `/readyz` 一直 503，reason 是「最近一次成功采集距今超过 180 秒」 | 调度器卡住 / 平台侧持续失败 | 看 ERROR 日志定位是哪一路失败；命令中心 3~8 秒的往返若频繁超时，看平台负载 |
| 慢 SQL 文本被截断 | 超过 `SQL_TEXT_MAX_LENGTH`（默认 512） | 截断是**显式标记**的（消息里会标）。需要更完整的 SQL 文本请调大，但要评估消息体膨胀与外发合规 |
