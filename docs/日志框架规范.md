# 日志框架规范 —— GaussDB TPOPS 采集端

面向运维与客户。采集端的日志框架是 **loguru 0.8.0**（纯 Python 包，
Python 3.7.9 可用，Linux + 3.7 下零传递依赖）。采集端**自己写文件**，
不依赖 logrotate（目标机是麒麟 V10 离线环境）。

与开发侧的对应关系：`changes/tpops-mapping-and-logging/design.md` 的决策 2/3/4/5/7
与 `changes/tpops-mapping-and-logging/specs/runtime-and-config/spec.md`。

---

## 1. 目录与文件布局

日志目录由 `LOG_DIR` 指定。`collector.sh run` 会把它设成 `<安装目录>/logs`
（`LOG_DIR` 没设时）；手工直接跑采集端且 `LOG_DIR` 也没设时**只写 stderr、不落盘**
（开发态的既有行为）。目录不存在会自动创建；**不可写 → 启动失败（退出码 2）**，
不静默降级成「只写 stderr」。

**6 个基名，每个基名按天一个文件，文件名带日期后缀**：

| 文件 | 内容 |
|---|---|
| `collector-<日期>.log` | **总日志**：启停、每轮整体汇总、**每个通道一行**的简洁汇总、WARNING 及以上 |
| `collector-monitor-<日期>.log` | A 类 监控指标通道：明细 + 该通道每轮汇总行 |
| `collector-command_center-<日期>.log` | B 类 命令中心通道 |
| `collector-diagnostic-<日期>.log` | C 类 诊断优化通道 |
| `collector-instance-<日期>.log` | D 类 实例元数据通道 |
| `collector-alarm-<日期>.log` | E 类 告警通道 |

`<日期>` = `YYYY-MM-DD`，例如：

```
logs/collector-2026-11-26.log
logs/collector-command_center-2026-11-26.log
```

**基名固定，不按指标名或实例名派生** —— 无论 87 个指标还是几百个实例，
日志目录里始终是这 6 个基名。

### 1.1 同一天内的切分

同一天内写超 `LOG_MAX_BYTES`（默认 **50 MB**）就切分：旧文件被**改名**为

```
collector-<日期>.<日期>_<时分秒_微秒>.log
```

（例如 `collector-2026-11-26.2026-11-26_14_23_45_123456.log`），
新的同名文件继续写。改名后的分片**同样在保留期清理范围内**。

## 2. 保留策略与磁盘占用

- 保留最近 `LOG_RETENTION_DAYS`（默认 **3**）个**自然日（含当天）**：
  今天、昨天、前天；日期更早的文件自动删除。
- 清理时机：进程启动时一次 + 每次跨天切分时一次。
- 按基名隔离：总日志的清理不碰通道日志，反之亦然。
- **磁盘占用上限** ≈ `6 个基名 × 3 天 × 50 MB ≈ 900 MB`（最坏估算）。
  实际远低于此 —— 默认只记汇总与关键事件，逐条明细在 DEBUG 级（默认不开）。

---

## 3. 总日志与通道日志的分工

| sink | 收什么 | 落点 |
|---|---|---|
| 总日志 | 生命周期、每轮整体汇总、**每个通道一行**的简洁汇总、WARNING 及以上 | `collector-<日期>.log` |
| 通道 sink ×5 | 该通道内部的采集与推送明细 + 该通道每轮汇总行 | `collector-<通道名>-<日期>.log` |
| stderr | 与总日志同内容（前台跑/调试时可见） | 终端 |

- **通道 INFO 明细不进总日志** —— 总日志要的是「一眼看出各采集器这一轮的情况」，
  不是明细洪水。
- **通道 WARNING 及以上两边都有** —— 总日志不能漏掉错误。
- 通道归属靠记录上的 `channel` 标记（`logger.bind(channel=...)`），
  通道 sink 按它过滤；**没带 channel 的记录只进总日志**。

> **开发态看不到通道明细**：stderr sink 与总日志同内容，所以前台跑时终端里没有
> 通道的 INFO 明细。要逐条看去 `logs/collector-<通道名>-<日期>.log`。

## 4. 格式

### 4.1 文本模式（`LOG_FORMAT=text`，默认）

用 **loguru 原生格式**（不是自研的 pattern 解析器）：

```
2026-11-26 14:23:45.123 | INFO     | tpops_kafka_collector.scheduler_report:59 - tick=12 elapsed=3.2s fetched=520 mapped=498 produced=498 failed=0
2026-11-26 14:23:45.456 | WARNING  | tpops_kafka_collector.collectors.command_center:88 - 命令中心任务超时 instance=inst-1
```

格式可用 `LOG_PATTERN` 覆盖（loguru 原生字符串语法）：

```
LOG_PATTERN={time:YYYY-MM-DD HH:mm:ss.SSS} | {level: <8} | {name} | {message}
```

### 4.2 JSON 模式（`LOG_FORMAT=json`）

每行一个 JSON 对象：

| 字段 | 含义 |
|---|---|
| `timestamp` | 采集时刻（ISO 8601） |
| `level` | 日志级别 |
| `logger` | 分层 logger 名（`collector.lifecycle` / `collector.<通道名>`） |
| `thread` | 线程名 |
| `message` | 消息正文 |
| `exception` | 异常堆栈（**仅异常路径有**） |

**汇总行的 `k=v` 会摊平成顶层字段**，日志平台可直接按 `channel` / `fetched` /
`produced` 取值，不必去解析 `message` 字符串：

```json
{"timestamp":"2026-11-26T14:23:45.123456+08:00","level":"INFO","logger":"collector.command_center","thread":"MainThread","message":"channel=command_center tick=12 ...","channel":"command_center","tick":"12","instances":"1","fetched":"520","mapped":"498","produced":"498","failed":"0","windows":"11","calls":"4","elapsed":"3.2s","delivery_rate":"1.000"}
```

### 4.3 红线

**口令、mini-token、业务 SQL 文本全文都不进日志** —— 写文件与写 stderr 同一口径。
第三方库（`kafka` / `urllib3` / `requests`）的日志已降噪到 `WARNING`，
并经转发器进入同一套 sink。

## 5. 每通道每轮汇总

每类采集器**完成一轮**（到期且跑完）后输出一条汇总行，**11 个字段固定**：

```
channel=command_center tick=12 instances=1 fetched=520 mapped=498 produced=498 failed=0 windows=11 calls=4 elapsed=3.2s delivery_rate=1.000
```

| 字段 | 含义 | 来源 |
|---|---|---|
| `channel` | 通道名（`monitor` / `command_center` / `diagnostic` / `instance` / `alarm`） | 通道常量 |
| `tick` | 轮次序号 | 调度器 |
| `instances` | 本轮该通道参与的实例数 | 通道 × 实例 |
| `fetched` | 从平台取回的原始行数 / 告警条数（**获取数据量**） | `TaskOutcome.fetched` 之和 |
| `mapped` | 幂等过滤后**尝试投递**的消息数 | `DeliveryStats.planned` 之和 |
| `produced` | **成功投递**的消息数（**已推送数据量**） | `DeliveryStats.delivered` 之和 |
| `failed` | 投递失败的消息数 | `DeliveryStats.failed` 之和 |
| `windows` | 本轮该通道执行的 SQL 条数 | `TaskOutcome.windows` 之和 |
| `calls` | 本轮该通道的外部调用次数 | `TaskOutcome.external_calls` 之和 |
| `elapsed` | 本轮该通道耗时（秒） | 通道级墙钟 |
| `delivery_rate` | 投递成功率（`produced / mapped`，`mapped=0` 时为 `1.000`） | 计算值 |

- **未到期的通道不输出汇总行**（通道各有各的采集周期，1/2/5/60 分钟分档）。
- 各通道的计数**之和等于**整体汇总行同名字段的值。
- 该行进**通道日志**；总日志里另有一行同字段的简洁版本。

## 6. 采集端的启动方式

| 命令 | 行为 |
|---|---|
| `bash collector.sh run` | **后台**启动：`setsid` + `nohup` 脱离终端、写 PID 文件、日志落盘；命令返回时进程已经在跑 |
| `bash collector.sh run --foreground` | **前台**运行 —— **systemd 用这个** |
| `bash collector.sh status` | 是否在跑 / PID / 运行时长 / 日志目录 |
| `bash collector.sh stop` | 按 PID 文件发 SIGTERM 优雅停止，最多等 30 秒再 SIGKILL，并清理 PID 文件 |

- PID 文件：`<安装目录>/run/collector.pid`；进程标准输出：`<安装目录>/run/console.out`。
- **重复启动会被拒绝**（已有实例在跑 → 返回非零并报出既有 PID），不会起第二个进程。
- **systemd 必须用 `--foreground`** —— `run` 默认后台化，systemd 需要前台进程才能
  托管与重启：

  ```ini
  ExecStart=/opt/tpops-collector/collector.sh run --foreground
  ```

## 7. 配置项

| 变量 | 默认值 | 说明 |
|---|---|---|
| `LOG_DIR` | —（`run` 时为 `<安装目录>/logs`） | 日志目录；留空 = 只写 stderr |
| `LOG_FORMAT` | `text` | `text` / `json` |
| `LOG_PATTERN` | — | 覆盖 text 模式的格式（loguru 原生字符串语法） |
| `LOG_MAX_BYTES` | `52428800`（50 MB） | 单个日志文件的大小上限，≥ 4096 |
| `LOG_RETENTION_DAYS` | `3` | 日志保留天数（自然日，含当天），≥ 1 |
| `LOG_LEVEL` | `INFO` | 日志级别 |

取值非法或日志目录不可写 → **启动失败（退出码 2）**，不静默降级。

## 8. 排障

| 症状 | 原因 | 处理 |
|---|---|---|
| 找不到日志文件 | `LOG_DIR` 指向别处，或采集端不是经 `collector.sh run` 起的 | `bash collector.sh status` 会打印实际日志目录；直接跑采集端且没设 `LOG_DIR` 时**只写 stderr、不落盘** |
| 日志目录报「不可写」 | `logs/` 属主不是服务用户 | `chown` 改成服务用户；**不要**绕过 —— 采集端不会静默降级 |
| `run` 报「采集端已在运行」 | 上一个实例还活着 | `status` 看状态；要停就 `stop` |
| `run` 返回 4 | 进程一起来就退了 | 先看 `run/console.out` 尾部，再看 `logs/collector-*.log` 尾部 |
| `status` 说「未运行（PID 文件残留）」 | 进程已死，PID 文件没清 | `bash collector.sh stop` 会清掉它 |
| 某通道日志是空的 | 该通道本轮没到期（周期不同） | 看总日志里的整体汇总行，确认本轮哪些通道到期了 |
| 日志里看不到通道的逐条明细 | 明细在 DEBUG 级 | `LOG_LEVEL=DEBUG`（日志量会明显变大） |
| 磁盘被日志占满 | `LOG_RETENTION_DAYS` / `LOG_MAX_BYTES` 配大了 | 调小这两个值；上限估算见第 2 节 |
