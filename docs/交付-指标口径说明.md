# GaussDB 指标口径说明（客户交付版）

> 本文档回答客户最关心的问题：**这 87 个指标，各自是从哪拿的、怎么算的、什么口径。**
>
> - 数据来源：`tpops_kafka_collector/mapping/data/metric_rules.json`（87 条指标规则，全部可提供）
> - 客户指标基准：`高斯DB-指标明细（客户要求的应该要提供的指标明细）.xlsx`「指标库」sheet
> - 生成方式：`python tools/build_delivery_docs.py`（表驱动，重跑输出不变）
> - 配套文档：《交付-不可提供指标清单.md》《交付-客户指标英文名核对清单.md》

客户指标库共 101 个指标：**87 个可提供**（本文档逐条说明口径），**14 个不在生效口径内**（11 条重复的英文变体 + 3 个无法提供 —— 已在**构建期**从生效口径移除，运行期不产出消息；见《交付-不可提供指标清单.md》与 `excluded_metrics.json`）。

## 1. 怎么读这份表

| 列 | 含义 |
|---|---|
| 客户指标英文名 | 就是客户指标库「英文名」列的值，投递到 Kafka 的 `metricCode` 字段 |
| 中文名 | 客户指标库「中文名」列的值，投递到 Kafka 的 `metricName` 字段 |
| 取数通道 | 走 TPOPS 的哪一条接口 |
| 来源 | 具体接口 / 平台指标名 / 合并 SQL 视图 |
| 取值规则 | 数据拿到之后**怎么变成客户的值**（求和？差分？取最后一个点？） |
| 声明周期 | 客户指标库「数据更新周期」列声明的**需求档**（= 映射表的 `collect_cycle`） |
| 实际产出频率 | 这条指标**实际**多久产出一条 —— 取所属通道的节奏（见 3.7），**不等于**声明周期 |
| 资源粒度 | 一条消息代表整个实例，还是按表 / 库 / 端口展开 |
| 归集口径 | 多 master 场景下这条消息出几条、值从哪来（见第 3 节） |
| 维度 | 指标名里的占位符，运行时会被替换成实际维度值（表名 / 库名 / 端口） |
| 备注 | 口径上的注意点与限制 |

> **占位符说明**：客户指标名里的 `{#NAME}` / `{#DATNAME}` / `{#PORT}` 是维度占位符，投递时替换成真实的表名 / 库名 / 端口号（例如 `gaussdb.{#NAME}.number.Of.index.scan` 里的 `{#NAME}` 会变成实际的表名），实际值同时放进 `tags.dimension_values`。

| 取数通道 | TPOPS 接口 | 指标数 | 实际产出频率 | 说明 |
|---|---|---|---|---|

## 3. 资源粒度与多 master 归集口径

这一节回答「**一条消息代表什么**」「**同一个实例有多个 master 时会出几条消息**」。

### 3.1 资源粒度

`resourceName` 按客户口径**只能表示一个节点**，固定为「节点 IP + 节点 ID」（模板 `{host_ip}_{node_id}`）。因此不同粒度的指标落在不同的地方：

| 资源粒度 | 指标数 | 消息形态 | 维度 |
|---|---|---|---|
| 实例级 | 63 | 一个实例一条（挂到第一个 master CN）；**A 类的实例级指标例外：逐组件各出一条**（见 3.5） | 无 |
| 表级 | 11 | 一张表一条（表名进指标名占位符） | `{#NAME}` |
| 库级 | 12 | 一个库一条（库名进指标名占位符） | `{#DATNAME}` |
| 端口级 | 1 | 一个端口一条（端口号进指标名占位符） | `{#PORT}` |

### 3.2 `node_scoped`：节点级视图 vs 实例级视图

命令中心的合并 SQL 会在**每个 master 节点各执行一次**，同一组视图因此返回多份结果。归集口径由映射表的 `node_scoped` 字段决定（该字段是**实测判定**的结论）：

> **本节只适用于命令中心（B 类）通道。**A 类（监控指标接口）走的是「逐组件各出一条」（见 3.5），C / D 类与节点无关（整条落到第一个 master CN）—— 它们都**不适用** master 维度的归集口径。

| 合并 SQL 视图 | `node_scoped` | 含义 | 产出条数 | 底层视图 |
|---|---|---|---|---|
| `activity_agg` | `true` | 节点级（各 master 值不同） | 每个 master 一条 | pg_stat_activity |
| `activity_running` | `true` | 节点级（各 master 值不同） | 每个 master 一条 | pg_stat_activity |
| `activity_top10` | `true` | 节点级（各 master 值不同） | 每个 master 一条 | pg_stat_activity |
| `bgwriter` | `false` | 实例级（各 master 值相同） | 只取第一个 master 的一条 | pg_stat_bgwriter |
| `database` | `false` | 实例级（各 master 值相同） | 只取第一个 master 的一条 | pg_database |
| `dbstat_sum` | `true` | 节点级（各 master 值不同） | 每个 master 一条 | pg_stat_database ⋈ pg_stat_user_tables |
| `locks` | `false` | 实例级（各 master 值相同） | 只取第一个 master 的一条 | pg_locks + pg_database |
| `prepared_xacts` | `false` | 实例级（各 master 值相同） | 只取第一个 master 的一条 | pg_prepared_xacts |
| `settings` | `false` | 实例级（各 master 值相同） | 只取第一个 master 的一条 | pg_settings |
| `stat_database` | `true` | 节点级（各 master 值不同） | 每个 master 一条 | pg_stat_database |
| `stat_user_tables` | `false` | 实例级（各 master 值相同） | 只取第一个 master 的一条 | pg_stat_user_tables |

- **节点级（`node_scoped = true`）**：各 master 的结果**各自成一份数据**，**不跨 master 合并、不求和**。实测同一实例三个 master 的 `pg_stat_database` 首行 `xact_commit` 分别是 153291 / 153299 / 146452 —— 求和会得到没有业务含义的 3 倍累计值。
- **实例级（`node_scoped = false`）**：各 master 返回相同的内容，**只取第一个 master CN 的一份**，不重复产出三份。
- **`master_view`**：实测出来的「各 master 是否一致」——`identical` 表示各 master 值相同（实例级），`divergent` 表示各 master 值不同（节点级）。本文档「归集口径」列已把它写进每一条指标。

### 3.3 多 master 的下发与去重

- 节点清单来自 `GET /rds/gaussdb/v3/instances/{id}/key-view-execute-node`，**同一个 `node_id` 会在清单里出现多次**（每个 node_id 同时以 CN 和 DN 各出现一条，实测 12 条清单条目只有 3 个唯一 `node_id`，其中 6 条 `role == "master"`）。下发前**按 `node_id` 去重**，否则会重复下发。
- 命令中心要求**只能在 master 节点执行**，所以下发的目标是**去重后的 master CN 列表**；实测一次下发多个 master 节点是成功的。
- 被选中的那个 master 在**各轮之间保持不变**（按节点清单顺序取第一个 master CN），资源名不会因为「这轮 SQL 在哪个 master 上跑」而漂移。

### 3.4 与节点无关的指标落在哪

命令中心的实例级 / 表级 / 库级指标、诊断优化指标、实例接口指标都**与具体节点无关**，统一挂到节点清单里的**第一个 master CN**（`role=master` 且 `type=CN`）上，保证跨轮稳定。

值与资源名**必须同源**：实例级指标的值取自承载资源名的那个 master。若该 master 本轮没有返回结果，且该指标的 `master_view` 不是 `identical`（值本来就可能因节点而异），**本轮不产出这条消息**，并记一条告警日志 —— 宁可少一条，也不用「A 节点的值配 B 节点的名字」。

### 3.5 A 类（监控指标接口）的多 series 归集

A 类的 11 个客户指标在客户库里都是**实例级一条**的消息，但平台按**组件**给出**多条 series**（例如 `rds092_gaussv5_commit_counter` 对 3 个 CN 各给一条 series，`datanode_switch_status` 对 9 个 DN 各给一条）。

**现状实现**：**逐组件各出一条**消息 —— 每条 series 一条，维度键 `COMPONENT_ID` 放进 `tags`，**不跨组件合成**；资源名取该组件所在节点的 `{host_ip}_{node_id}`（组件换算不到节点时回落到第一个 master CN）。

下面是**用采集端代码回放 `data/metric_response/` 里的原生响应实测**的条数（每个指标各一条消息 × 该指标的组件数）：

| 客户指标 | 平台指标 | 一轮产出的消息条数 | 组件 |
|---|---|---|---|
| `gaussdb.Tps` | `rds400_gaussv5_total_counter` | 3 | 3 个 CN |
| `gaussdb.QPS` | `rds402_gaussv5_ddl_dml_dcl_count` | 6 | 3 个 CN + 3 个 DN |
| `GAUSSDB.Standby_status` | `datanode_switch_status` | 9 | 9 个 DN |
| `GAUSSDB.Primary_status` | `datanode_switch_status` | 9 | 9 个 DN |
| `gaussdb.Starttime` / `gaussdb.Uptimestr` | `rds133_cn_startup_time` | 各 3 | 3 个 CN |
| `GAUSSDB.Number_of_ansactions_mmitted_r_cond` | `rds092_gaussv5_commit_counter` | 3 | 3 个 CN |
| `GAUSSDB.Number_of_llback_ansactions_r_cond` | `rds093_gaussv5_rollback_counter` | 3 | 3 个 CN |
| `GAUSSDB.Service_availability_testing` / `GAUSSDB.PG_Service_Status` / `gaussdb.Status` | `gaussdb_instance_status` | 各 1 | 单值 |

> **客户按「一个实例一条」估算 A 类消息量会算少**：上表里最多的一个指标一轮就出 9 条。合成口径（速率类求和 / 启动时刻取最早 / 主备状态按 DN 展开或归集为布尔）属业务口径，**待客户确认**；确认后由映射表的 `value_rule` 承载，不改消息信封。

### 3.6 累计计数的差分基线按节点隔离

需要差分算速率的累计计数类指标（每秒 Fetch / Insert / Return / Update / Delete 记录数），基线按**节点**隔离：基线键是二元组 `(指标名, 作用域:维度)`，作用域一般是 `node_id`（必要时还带实例 ID）—— 效果等价于「指标名 + 维度 + 节点」三元组，避免多个 master 共用一个存储时互相覆盖基线、算出跨节点的假速率。

### 3.7 声明周期 ≠ 实际产出频率（**超服务**，请按实际频率配容量）

这一节是**容量与带宽口径**，请客户重点看。

| 口径 | 含义 | 来自哪里 |
|---|---|---|
| **声明周期** | 客户指标库「数据更新周期」列声明的**需求档** | 客户指标表 / 映射表的 `collect_cycle` |
| **实际产出频率** | 这条指标**实际**多久产出一条 | **所属通道**的调度周期（该通道内最高需求档 = 最短周期） |

**当前实现里没有按指标 `collect_cycle` 的产出闸门** —— 采集器一轮会把该通道的**全部**规则都产出。因此**同一通道里的所有指标都按该通道的频率产出**，与各自的声明周期无关。

| 取数通道 | 实际产出频率 | 覆盖指标数 | 通道内的声明周期分布 |
|---|---|---|---|
| 监控指标接口 | 30 秒 | 11 | 1 分钟、30 秒、5 分钟、60 秒 |
| 命令中心SQL | 1 分钟 | 71 | 1 分钟、2 分钟、24 小时、5 分钟、60 秒 |
| 诊断优化接口 | 2 分钟 | 4 | 2 分钟、5 分钟 |
| 实例接口 | 1 小时 | 1 | 1 小时 |

**54 个指标的声明周期慢于其通道的实际节奏**（即「超服务」）：它们**按通道频率**产出，不是按声明周期。

> 影响客户侧的量级：按「每条规则每轮一条」估算，单个实例**每天至少 136,824 条**指标消息（A 类的多 series 展开、表级 / 库级 / 端口级指标的按行展开会让实际条数**更多**）。客户侧请按这个量级准备存储与带宽，并**按「实际产出频率」列**配置保留策略与告警阈值；若需要按声明周期节流，需要我们增加产出闸门（改采集端逻辑，不改消息格式）。

## 4. 取值规则类型说明

87 个指标一共用了 13 种取值规则（`value_rule.type`），逐条口径见第 5 节。

| 规则类型 | 人话口径 | 指标数 |
|---|---|---|
| `raw` | 直接取某一列的值（求和 / 一行一条 / 取第一行，由 `row_policy` 决定） | 43 |
| `aggregate` | 按条件过滤后分组求和（分母/分子类的条件聚合） | 12 |
| `series_point` | 取时序上的一个点（平台按组件给多条 series） | 9 |
| `counter_delta` | 累计计数**跨轮差分**算速率（本次值减上轮值 ÷ 实际间隔秒数） | 5 |
| `raw_filtered` | 按条件过滤后取**首个**匹配行的某一列 | 4 |
| `raw_rows` | 整行列表原样透传（明细型指标） | 3 |
| `top_n` | 按排序列取前 N 条（可投影字段） | 3 |
| `ratio_across` | 跨视图的分子 ÷ 分母（分母取不到就不产出） | 2 |
| `text_prefix_count` | 按 SQL 文本前缀给集合分类计数 | 2 |
| `collection_count` | 统计诊断优化接口某个集合的条数 | 1 |
| `enum_map` | 时序点的值按枚举表翻译（未命中原样透传并告警） | 1 |
| `gauge` | 由平台给的启动时刻推算已运行时长 | 1 |
| `instance_field` | 取实例元数据里的一个字段 | 1 |

## 6. 口径上的通用约定

1. **缺值不产出假数据**：取不到值时该指标本轮不产出消息，不填 0、不填上一轮的值。
2. **先投成功再推进水位**：一轮的顺序是「拉取 → 转换 → 投递 → 成功后推进水位」，投递失败不推进水位，重启后从水位续传（至少一次语义）。
3. **值的线格式**按客户指标库「数据类型」列序列化：整数 / 浮点转数字，文本转字符串；文本型明细指标按原样带出（列表）。两份对接方案的文件字段表都写 `value` 是 String，这一项**待客户确认**。
4. **慢 SQL 文本默认脱敏**：SQL 字面量替换为 `?` 并截断到 512 字符，是否允许外发原始 `sql_text` **待客户书面确认**。

## 7. 仍需客户确认的口径项

以下几项已按默认值实现，确认后只改映射表即可，不改采集逻辑（完整清单见 `tpops_kafka_collector/mapping/data/open_items.json`）：

| 事项 | 当前默认口径 |
|---|---|
| A 类多 series 归集 | 逐组件各出一条消息，`COMPONENT_ID` 进 `tags`（见 3.5） |
| 状态类指标的展示值 | 平台枚举值原样透传（实测 1=正常、0=异常） |
| 采集频率 | **实际产出频率**取通道周期（监控指标 30 秒 / 命令中心 60 秒 / 诊断优化 120 秒 / 实例 3600 秒）；客户指标库的「数据更新周期」是**声明周期**，当前**不作为产出闸门**，同通道指标一律按通道频率产出（见 3.7） |
| `value` 的线格式 | 按客户指标库「数据类型」序列化 |
| 慢 SQL 的 `sql_text` | 默认脱敏 + 截断 512 字符 |
| `resourceName` 与台账对齐 | `{host_ip}_{node_id}`，待客户提供台账清单后核对 |
