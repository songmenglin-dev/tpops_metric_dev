## 六、第二轮事实核对新增（已复现，2026-11-06 补）

### ⭐ B-13/B-14 已用实测探针解决（2026-11-06，`data/multi_master_probe/`）

针对 master 节点做了两个探针，**结论推翻了方案里一条承重假设**：

| 探针 | 结果 |
|---|---|
| **A：一次下发 3 个 master 节点** | **HTTP 200**，`node_tasks` 3 条，`statistics {total:3, succeed:3, failed:0}`，**3 个任务全部返回数据** |
| **B：逐个 master 单独下发同一条 SQL** | 库列表相同（5 个库），但**计数值不同**：`postgres.xact_commit` = 7265656 / 7218577 / 6315580；`numbackends` = 24 / 26 / 26 |

**由此确定三件事：**

1. **「一次下发多节点会失败」是错的** —— 该结论的实测来源是
   `data/command_center/results/07_task_result_matrix_u_shell_sync.json`，
   那是 **SHELL 命令**的 `result` 里出现 `Failed to execute command on all nodes.`，
   被**错误地推广**到了 SQL 命令。SQL 命令一次下发多个 master 完全正常。
   → 已修正 `CLAUDE.md`、`data/tpops_api_catalog.json`（2 处）、方案正文（6 处）。
2. **master-only 是命令级约束，不是指标级** —— 出处只有 API 响应里的
   `constraint_config.limit_node_types: ["master"]`
   （留档 `data/command_center/results/04_command_detail/73722acc-….json`）。
   **CHM 产品文档 `docs/api/` 里没有这条**（只列了命令中心的接口与权限项）。
   82 个 B 类指标是顺带继承的；平台另有 74 条 SQL 命令，其节点约束**未查详情**
   （命令列表接口不暴露 `constraint_config`）。
3. **B-14 的汇总语义现在是实测已知的**：各 master 返回**不同的计数** →
   选任一 master 只是该节点视角。要整实例口径必须**一次下发全部 master 并按节点分基线再汇总**。

| 错误类型 | 例子 | 影响 |
|---|---|---|
| **来源列写成表达式而非真实列/别名** | `pg_stat_activity.state`、`pg_locks`、`blks_hit/(blks_hit+blks_read)` | 照此无法从 SQL 结果取值；启动校验会失败 |
| **规则类型错配** | 3 行标 `raw_rows` 实为 `group by + count(*)` 聚合；ratio 行 SQL 已算成百分比别名却仍标 `ratio` | 规则引擎无法执行 |
| **单位是 `/s`、`tuples/s`、`buffers/s` 但规则是 `raw` 取累计量** | 16 行 | **值形态错误**（应差分）—— 与 M-10 的性能基线问题同源 |
| **"必须写 as 别名" 与文档自带 10 条 SQL 及实测矛盾** | 实际只需**派生列**写别名 | 约束过度，会写出冗余 SQL |

→ **修复方式应是：从 `data/metric_verification/` 的实测响应 + `data/customer_metric_query_plan.json`
机械重生成这张表**，而不是人工逐格修补。理由：这些单元格每一个的"正确值"都能从留档唯一确定。
