## 3. 平台接口实测清单（本次补做的依据补强）

| 接口 | 用途 | 状态 |
|---|---|---|

## 4. 发现的判定偏差（本轮不修改，留作下一轮输入）

### 偏差 1 —— 漏判：客户「版本」应可提供

- 客户指标：`gaussdb.server_version`（基本信息，1 小时）
- 现判定：**无法提供**，note「平台无实例版本指标」
- 实测：`GET /rds/v3.2/instances` 返回 `engine_version = "V2.0-10.0.0"`（已存于 `data/instances.json`）
- 问题：原判定只查了指标接口，漏了实例详情接口 → **假阴性**
- 建议：改为可提供，来源标注为「实例详情接口 engine_version（非指标接口）」

### 偏差 2 —— 漏判：客户「空闲连接数」可推导

- 客户指标：`gaussdb.Idle_conn`（连接情况，1 分钟）
- 现判定：**无法提供**，note「平台无 idle 连接口径」
- 推导路径：`rds143_gaussv5_online_session`（在线会话数量）− `rds117_gaussv5_active_session`（活跃会话数量）
- 问题：平台无独立 idle 指标，但可由两项相减得到 → 判定偏严
- 建议：改为可提供，match_level 标「可推导」

### 偏差 3 —— 偏松：客户「写/读块的时间」口径不符

- 客户指标：`gaussdb.Blk_write_time` / `gaussdb.Blk_read_time`（性能信息，1 分钟）
- 现判定：**可提供 / 近似对应** → `sys075_avg_disk_ms_per_write` / `sys076_avg_disk_ms_per_read`
- 问题：客户要的是 `pg_stat_database.blk_write_time` —— **数据库层累计耗时**；平台给的是**磁盘单次写入平均耗时**。层级（DB vs 磁盘）与口径（累计 vs 平均）都不同，推给客户会误导
- 建议：降为无法提供，或保留可提供但把 match_level 由「近似对应」改为更明确的标注

### 依据不足 1 —— #12 服务端口检测

- 现判定：无法提供，note 仅写「平台无端口探测类指标」
- 补充依据：CHM 中存在 `GET /v3/instances/{instance_id}/port`，**本平台实测 404（未实现）**
- 建议：note 改为「平台未实现 /port 接口」，便于向客户说明是平台裁剪而非功能缺失

### 依据不足 2 —— #43 / #45 映射到 `rds089` 的实例覆盖

- `rds089_gaussv5_inuse_counter`（CN连接数）在实例 `83cd68f2` 上有数据，在实例 `c35b8d07` 上**无数据**
- 建议：note 补「实例 c35b8d07 无该指标数据」，避免客户按两实例都有的预期去对数

## 5. 结构性缺口分析

### 5.1 69 条无法提供的原因归类

| 缺口类型 | 条数 | 典型客户指标 |
|---|---|---|
| 表级维度 | 23 | `({#NAME})` 死元组 / 删除行数 / 索引扫描 / 顺序扫描…（表信息 11 条 + 事务信息 12 条） |
| 库级维度 | 8 | `[{#DATNAME}]` 提交/回滚事务数、各类每秒记录数、缓存命中率 |
| SQL / 会话明细 | 6 | 正在运行的 SQL、Top10 SQL、会话 TOP10、慢查询 Select/DML 拆分 |
| 其他 / 口径缺失 | 32 | bgwriter 8 条、临时文件、冲突次数、版本字符集时区页大小、idle/预提交/禁用连接、Agent 项、采集接口项 |

### 5.2 反向缺口：TPOPS 有但客户不要

32 条客户指标只用到 **26** 个 TPOPS 指标；TPOPS 216 个有数据的指标里 **190 个客户一条都没要求**：

| TPOPS 分组 | 客户未要求的数量 |
|---|---|
| TRANSACTION | 58 |
| CONNECTION | 25 |
| CPUMEMORY | 22 |
| PROCESSRESOURCE | 20 |
| INSTATUS | 18 |
| LOCK | 13 |
| NETWORK | 12 |
| IOSTORAGE | 11 |
| SYNCSTAT | 8 |
| AGENTSTATUS | 3 |

**客户 101 项里没有任何 CPU / 内存 / 磁盘 / 网络指标** —— 这套指标库是照着 openGauss/GaussDB 的 `pg_stat_*` 指标清单开的，而 TPOPS 强项在系统资源层。两者几乎不重叠，这是 32/69 这个比例的根本原因，不是映射做得不好。

### 5.3 维度与口径的三处系统性差异

| 客户要求 | TPOPS 实际 | 影响条数 |
|---|---|---|
| 库级占位符 `[{#DATNAME}]` | 只有「系统库 / 业务库」两个固定维度 | 8 |
| 表级占位符 `({#NAME})` | 无表维度 | 23 |
| 累计值（事务总数、块数） | 速率（次/秒、block/秒） | 6（已标「需换算」） |

## 6. 待与客户确认的问题

1. **维度降级**：库级/表级指标能否接受实例级聚合口径？（23 + 8 = 31 条，占无法提供的 45%）
2. **累计值 vs 速率**：客户要累计、平台给速率，是否由采集侧累加后输出？
3. **补采集路径**：这 31 条维度不匹配的指标，走《数据库监控接入操作指引》里其余数据库的 **Agent 采集 `pg_stat_*`** 路线是否可接受？若可，则 101 项可全量覆盖。
4. **同名不同义**：`gaussdb.Blk_write_time`（DB 层累计）与平台 `sys075`（磁盘单次平均）不能混用，需明确客户能否接受平台口径。
