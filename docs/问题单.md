## 1. 数据正确性

### [x] TPOPS-001 跨 schema 同名表 → 维度值不唯一 → 后一条被静默丢弃

**严重度** 高 ｜ **状态** 已关闭 ｜ **类别** 数据正确性

> **解决方式（wave-1）**：表级指标的维度值改成 **`schema.table`**
> （`mapping/rules_context.py`：绑定 ``schemaname.relname``，两个列的值用 ``.`` 连起来；
> 分组键同时含这两列）。不同 schema 的同名表因此拿到**不同的维度值** → 不再撞幂等键，
> 也不再出现「分组键重复」的 WARNING。**方案取的是 (c)**（schema 进维度值）——
> 不动客户的 `metricName` 字段规范。

**现象**

不同 schema 下存在同名表时，表级指标的维度值（`{#NAME}` = 表名）不唯一。
`tags.dimension_values` 里只有表名、没有 schema → 两张同名表算出**同一个幂等键** →
采集端投递前 `if key in seen: continue`（`tpops_kafka_collector/scheduler_delivery.py:81`）
**把后一条静默丢掉**。客户侧只会收到一张表的数据，且不知道丢的是哪一张。

**证据**（客户现场实采）

| 实例 | 表数 | 重名组数 | 例子 |
|---|---|---|---|
| 83cd68f2… gauss-6374（Combined） | 69 | **0** | — |
| c35b8d07… gauss-75a2（Ha） | 447 | **9** | `t_auto`（cotest / ods_new）、`user_info`（demo_schema / root）、`TW_SYS_USER_TEMP_0817`（jchk0817 四个变体）、`fl_151_v3_01`、`TEST_USER1`、`T_AUTO`、`T_ID`、`t_id`、`snapshot`（db4ai / snapshot） |
| 82e93fe8… gauss-6009（Ha） | 76 | **1** | `snapshot`（db4ai / snapshot） |

采样佐证：`t_auto` 只出了 22 条消息（22 个指标 × 1），而不是 44 条（× 2 个 schema）。

**影响** 客户侧表级指标**少一半**（同名的那几张表），且无任何提示。

**方案（待选）**

- (a) 维度里加 schema → 改客户字段规范（`{#NAME}` 只允许一个占位符），需客户书面同意；
- (b) 同名表**合并成一条**（计数类求和）→ 语义变成「叫这个名字的所有表」，需客户确认；
- (c) schema 放进 `tags.dimension_values`（不动 `metricName`）→ 客户按 tags 区分，
  但客户的入库主键若不含 schema 仍会撞。

**验收** 目标实例之外，出现同名表时每张表都有独立消息（或按客户确认的合并口径），
且日志里不再出现 `分组键重复` 的 WARNING。

**关联** `tpops_kafka_collector/mapping/rules_context.py:148`（告警点）、
`tpops_kafka_collector/scheduler_delivery.py:81`（丢弃点）、`data/mapping/metric_rules.json`

### [ ] TPOPS-002 速率型指标发的是原始累计量（10 个指标）

**严重度** 高 ｜ **状态** 待办 ｜ **类别** 数据正确性 ｜ **阻塞交付**

**现象**

客户指标表里单位标成速率（`tps` / `tuples/s` / `scans/s`）的指标，采集端发出去的是
**原始累计计数**（`pg_stat_database.xact_commit`、`pg_stat_user_tables.n_tup_upd` 等）。
客户按速率画图会离谱地大（例：`postgres` 的每秒提交事务数 = 23,553,503）。

**证据**（客户现场实采 + 平台现查逐条比对）

| metricCode | 客户表单位 | 我们发的值 | 实际口径 |
|---|---|---|---|
| `GAUSSDB.[{#DATNAME}]_committed_transactions` | tps | 347,588（lz） | `xact_commit` 累计 |
| `GAUSSDB.[{#DATNAME}]_rolled_back_transactions` | tps | 0 / 26 | `xact_rollback` 累计 |
| `GAUSSDB.{#NAME}.number.Of.update.tuples` | tuples/s | 累计 | `n_tup_upd` 累计 |
| `GAUSSDB.{#NAME}.number.Of.insert.tuples` | tuples/s | 累计 | `n_tup_ins` 累计 |
| `GAUSSDB.{#NAME}.Number.lete.ples` | tuples/s | 累计 | `n_tup_del` 累计 |
| `GAUSSDB.{#NAME}.Number.t.date.ples` | tuples/s | 累计 | `n_tup_hot_upd` 累计 |
| `GAUSSDB.{#NAME}.number.Of.index.scan` | scans/s | 累计 | `idx_scan` 累计 |
| `GAUSSDB.{#NAME}.number.Of.sequential.scan` | scans/s | 累计 | `seq_scan` 累计 |
| `GAUSSDB.{#NAME}.number.Of.quential.ples.ad` | tuples/s | 累计 | `seq_tup_read` 累计 |
| `GAUSSDB.{#NAME}.number.Of.dex.ples.ad` | tuples/s | 累计 | `idx_tup_fetch` 累计 |

对照：同族 4 个 `GAUSSDB.[{#DATNAME}]_*_records_per_second` 用 `counter_delta`（差分），
发出去的值是 0/2/85 —— **口径是对的**。所以同一张客户指标表里，10 个用 `raw`、4 个用
`counter_delta`，是**我们这边的不一致**。

**方案** 把这 10 条规则的 `value_rule.type` 从 `raw` 改成 `counter_delta`
（与 `*_records_per_second` 同款）。**只改映射表，不改代码。**
注意：`counter_delta` 依赖跨轮差分基线，**首轮没有基线 → 不产出**（不是 0）；
且差分窗口 = 采集周期（5 分），值是「每 5 分钟的增量」，要不要再除以秒数换算成
「每秒」需与客户确认（客户表的「数据更新周期」是 5 分钟）。

**验收** 这 10 个指标的值量级与平台现查的增量一致；首轮无基线时不产出、不报 0。

**关联** `data/mapping/metric_rules.json`（规则表）、
`tpops_kafka_collector/mapping/rules_cross.py`（`counter_delta` 实现）

### [x] TPOPS-003 11 组英文名仅大小写不同、中文名不同

**严重度** 中 ｜ **状态** 已关闭 ｜ **类别** 客户口径

> **解决方式（wave-1）**：按「**保留中文名正常的一套**」落地（小写 `gaussdb.` 前缀），
> 大写 `GAUSSDB.` 前缀的 11 条**在构建期**进排除清单
> （`tpops_kafka_collector/mapping/data/excluded_metrics.json`，reason=duplicate）——

英文名相同、中文名不同 —— 全部是表级指标：

| `gaussdb.{#NAME}.Number.ad.ples` | ({#NAME})已删除但未回收的行数（死亡行） | ({#NAME}) number of dead tuples |
| `gaussdb.{#NAME}.Number.lete.ples` | ({#NAME})被删除的行总数（包括已回收行） | ({#NAME}) number of delete tuples |
| `gaussdb.{#NAME}.number.Of.dex.ples.ad` | ({#NAME})通过索引扫描获取的行数 | ({#NAME})number of index tuples read |
| `gaussdb.{#NAME}.number.Of.index.scan` | ({#NAME})索引扫描次数 | ({#NAME})number of index scan |
| `gaussdb.{#NAME}.number.Of.insert.tuples` | ({#NAME})插入的行数 | ({#NAME})number of insert tuples |
| `gaussdb.{#NAME}.number.Of.live.tuples` | ({#NAME})当前活跃的行数 | ({#NAME})number of live tuples |
| `gaussdb.{#NAME}.number.Of.quential.ples.ad` | ({#NAME})顺序扫描读取的行数 | ({#NAME})number of sequencial tuples read |
| `gaussdb.{#NAME}.number.Of.sequential.scan` | ({#NAME})顺序扫描次数 | ({#NAME})number of sequencial scan |
| `gaussdb.{#NAME}.number.Of.update.tuples` | ({#NAME})更新的行总数 | ({#NAME})number of update tuples |

**影响** 两套**都投递**，`metricCode` 只差前缀大小写、**值完全一样**（同一列同一口径，

（ES、部分数据库默认折叠）→ 这 11 个指标会**合并成一条、互相覆盖**。

**要客户回答** 是两条独立指标，还是同一条的重复登记？若是后者，保留哪一套
（值一样，留 2 分钟那套更及时）。

**关联** `docs/交付-客户指标英文名核对清单.md` §5「同名指标两套写法」那一行
（目前只有一句概括，本表可作为它的展开）、`data/mapping/metric_rules.json`

### [ ] TPOPS-006 多实例并行 → 一轮耗时超过轮询间隔

**严重度** 中 ｜ **状态** 待办 ｜ **类别** 稳定性

客户现场 3 个实例时，一轮 **31.6 s > 30 s 轮询间隔**，触发
「本轮耗时超过轮询间隔 —— 重新锚定到当前时刻」；`单轮外部调用数 70 超出预算 42`。
实例更多时更明显。采集端**本来就该采全部实例**（不写死 ID），所以要调的是**节奏**，
不是范围。

**方案（待选）** 调大轮询间隔 / 按实例错峰 / 放宽外部调用预算 / 减少重复取数
（`单轮调用数超出预算 —— 检查是否有重复采集` 这条告警本身也要查）。
